# INFINITY — کیت تست v35 / F4 شناسایی ثابت‌ها + دامپ (نسل یازدهم)

## این پکیج چیست؟

**درایور v26 (بدون هیچ تغییری) + اسکریپت v35** — **F4: شناسایی ثابت‌ها
(RECON) + دامپ .data — بدون op-12.** رانگ v34 دومین کرش پروژه رو داشت
(BSOD 0x50، مثل v33) و این بار، به لطف پارامترهای کامل باگ‌چک که توی
step 0 گزارش v34 ثبت شده بود، **قاتل واقعی با اثر انگشت ریاضی پیدا شد —
و چیزایی نبود که فکر می‌کردیم.**

## صادقانه: تحلیل v33 اشتباه بود — قاتل واقعی چین B است

توی گزارش v34، step 0 این خط رو چاپ کرد (پارامترهای کامل کرش v33 که
قبلاً نداشتیم):

```
BUGCHECK 0x50 (0xfffff807154e5078, 0, 0xfffff8071d08707c, 0)
```

حسابش کنید: `0xfffff807154e5078 - 0xfffff807154e0000 = 0x5078` و
`0x1AD × 0x30 + 8 = 0x5078` **دقیقاً.** یعنی:

- `0x1AD` = شماره قاب فیزیکی PML4 سیستم (همون dtb=0x1AD000 که رانگ v33
  خودش اکو کرده بود، شیفت‌خورده ۱۲ بیت)
- `×0x30` = اندازه هر ساختار `_MMPFN`
- `+8` = آفست فیلد `PteAddress`

این دقیقاً **خط ۳۴۷ کد درایوره**: `slot = pdb + pfn×0x30 + 8` که بعدش
**خام deref می‌شه** — خواندن `_MMPFN[0x1AD].PteAddress` از چین B، با یک
`pdb` **زباله**: یک پوینتر کرنلیِ تصادفی که از یکی از ۵ RVA تحقیق‌شده‌ی
`MmPfnDatabase` خونده شده و چک ضعیف «canonical + page-aligned» بهش راه
داده. صفحه‌ی مقصد مپ نبوده → فالت → 0x50.

**چرا فرمول‌ها مقصر نبودن:** چین A (کاندیداهای `MmPteBase`) روی هر دو
بوت پاس شد — یعنی base درست بوده. با base درست، همه‌ی آدرس‌های فرمول
قدیمی v25 **داخل محدوده‌ی مپ‌شده‌ی PTE-space** می‌افتادن — خواندنشون
هیچ‌وقت فالت نمی‌ده (فقط داده‌ی غلط می‌داد). باگ فرمول v25 واقعی بود و
فیکس v26 درست — ولی **بی‌ربط به مرگ VM**. فیکس v26 ثابت‌های PFN رو
«intact» نگه داشت و همون خط زهرآلود، VM رو دومین بار کشت.

**نتیجه‌ی درس‌آموخته:** دیگر هیچ deref خامی از ثابت‌های «تحقیق‌شده».
اول داده‌ی واقعی این بیلد رو جمع می‌کنیم، بعد walk می‌فرستیم.

## استراتژی v35 — فیل‌بسته تا مغز استخوان

1. **op-12 بازنشسته (RETIRED).** اسکریپت v35 **هیچ‌وقت** op-12 نمی‌فرسته.
   یعنی همون اوپی که دو بار VM رو کشت، این رانگ اصلاً صدا زده نمی‌شه —
   بحران غیرممکنه.
2. **همه‌چیز از دروازه‌ی اثبات‌شده:** op-1 فقط داخل بازه‌ی ایمیج
   (L1-L5 از v20 به اثبات رسیده) + op-11 (همون W قدیمی).
3. **[R] RECON:** هفت کاندید (دوتا `MmPteBase` + پنج‌تا `MmPfnDatabase`)
   با خواندن ۸ بایتی از داخل ایمیج + اکوی dtb از op-11. مقادیر واقعی
   این بیلد + چک شکل PTE-base سمت اسکریپت + گاردهای برخورد
   (s=0x100 [مقدار MmSystemRangeStart] و s=0x1EF [اسلات KUSD]).
4. **[D] دامپ .data:** کل سکشن .data با همین دروازه، تکه‌های ۱۰۲۴ بایتی،
   خودتأیید‌شونده (بایت‌های اول باید MZ و e_lfanew رو اکو کنن)،
   قابلیت resume (فایل marker)، مانیفست + sha256.
5. **step 0 گسترش‌یافته:** پارامترهای کامل باگ‌چک‌های جدید (کرش v34 هم
   باید همون اثر انگشت `+pfn×0x30+8` رو نشون بده) + اشاره به Minidump.
6. **W2 با تلورانس exit-race:** PID 656 توی v34 بین walk و اسنپ‌شات
   خارج شده بود — الان re-query می‌شه و «خارج‌شده» تحمل می‌شه (تا ۱ مورد).

## انتظار رانگ v35

- **K/L/M/J/W سبز برای نهمین بار** (رگرسیون کامل + W2 با تلورانس جدید)
- **[R1/R2]:** اگر کاندید MmPteBase شکل درست داشته باشه: پیام
  `*** PTE-BASE SHAPED: s=0x... ***` — یعنی base واقعی این بیلد همون‌جاست
- **[R3..R7]:** مقادیر واقعی کاندیداهای PFN — احتمالاً پوینترهای زباله
  (همون کلاس قاتل) یا صفر — هر کدوم باشه، **مدرک کالبدشکافیه**
- **[D] دامپ:** انتظار ~۲۰۰۰ تا ~۴۰۰۰ تکه (چند دقیقه تا ~۱۵ دقیقه بسته
  به سرعت VM — خط پیشرفت + ETA نشون داده می‌شه). موقع دامپ VM کاملاً
  زنده و پاسخگوئه — فقط ترافیک hook زیاد می‌شه.
- **INFCNT نهایی = G+8+anSent+mNameWrites+wSent+rSent+dumpSent** (اسکریپت
  خودش عدد دقیق رو محاسبه و چاپ می‌کنه)
- **VERDICT:** `F4 RECON COMPLETE + GROUND-TRUTH DUMP CAPTURED (the VM SURVIVED)`

## چی رو بفرستید؟

**همون فلوی همیشگی + سه فایل جدید:**

1. `trigger-test-v35-output-*.txt` (ترنسکریپت)
2. `serial-phase-d.log` (تا وقتی که هست — این بار بعد از ریبوت بازنویسی
   می‌شه، نگران نباشید اگر ناقص بود)
3. عکس صفحه‌ی بوت + عکس PowerShell (اگر BSOD نبود که عالی — عکس صفحه‌ی
   پایان اسکریپت با verdict کافیه)
4. **`ntoskrnl-data-*.bin`** (خروجی دامپ — چند مگابایت)
5. **`ntoskrnl-data-*.manifest.txt`** (مانیفست)

بعد از این: آفلاین مقدار واقعی `MmPteBase` (و هر چیزی که توی اون RVAها
هست) از خود بایت‌های دامپ درمیاد، و **کیت v36** (walk نهایی F4 با
ثابت‌های راستی‌آزمایی‌شده + چین B بازنشسته) ساخته می‌شه — بدون حدس،
بدون درز، بدون کرش سوم.

## چرا این رانگ نمی‌تونه کرش کنه؟

هر خواندنی که v35 انجام می‌ده یکی از این دوتاست:
- **داخل بازه‌ی ایمیج** `[pe_base, pe_base+pe_size)` — همون دروازه‌ای که
  L1 تا L5 از v20 تا امروز ۹ بار در میدان اثبات شده
- **op-11** — همون walk پروسه که W1 تا W5 رو هشت بار سبز کرده

op-12 اصلاً فرستاده نمی‌شه. تنها کار ریسکی این اسکریپت، خوابیدنه 🙂
