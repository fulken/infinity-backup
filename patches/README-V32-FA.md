# پکیج v32 — درایور v24 + اسکریپت v32 (رفع باگ deref: پیاده‌روی از خودِ EPROCESS، نه از VA سمبل)

## خبر فیلد v31: فیکس اکسپورت اثبات شد ✅ — ولی پیاده‌روی در گِیتِ تازه‌ای ایستاد 🔬

اجرای v31 (۲۰۲۶-۰۹-۲۷ ساعت ۱۹:۵۱) **صفر کرش، VM زنده تا آخر، رونوشت کامل ۴۳۵ خط**:

- **M کاملاً سبز شد — فیکس v23 در فیلد اثبات شد**: M1 دقیقاً روی
  `0xFFFFF8071A4FC420` (سومین اثبات مستقل این مقدار)، M2r بیلد **19045**،
  M3 هشت بایت کد واقعی KeBugCheckEx، و M4 حالا rc=7 درست (در v30 همه rc=4
  بودند).
- **F1 + F2 برای پنجمین بار متوالی روی باینری جدید اثبات شدند**: K همگرا،
  L1..L5 سبز، ماتریکس J صددرصد، INFCNT = 31 دقیقاً فرمول.
- **ولی W هنوز رد شد** — این بار با امضای متفاوت: `payload status@1024=4`
  (not-System)، `walk=0`، `closed=0`، `name slot=0`، `pages=0` و سریال
  `[PW] sys=0xFFFFF8071A4FC420` → بلافاصله `walk=0`.

## ریشه: یک deref جاافتاده — دقیقاً در یک خط ✋→🔬

`PsInitialSystemProcess` یک **متغیر اشاره‌گر** در .data خودِ ntoskrnl است؛
`kx::Resolve` آدرسِ **خودِ خانه‌ی** اشاره‌گر را برمی‌گرداند (0xFFFFF8071A4FC420
— داخل image)، نه EPROCESS را. EPROCESS سیستمی در `*(u64*)خانه` است — یک
آبجکت pool **بیرون از** image (مثل KPCR در 0xFFFF8E808758B000). op-11 در v23
همان VA سمبل را مستقیم به `WalkCore` می‌داد:

```c
wr = pw::WalkCore(s1.resolved_va, ...);   // v23: خوندن pid@سمبل+0x440 = زباله‌ی .data
```

پس پیاده‌روی می‌رفت `0xFFFFF8071A4FC420+0x440` را می‌خواند (دیتای .data!)،
۴ نبود → **not-System** در همان چک اول. **یک deref مفقود، همه‌ی بایت‌های
مشاهده‌شده را توضیح می‌دهد**: `pages=0` (return زودهنگام)، `sysEntry=0`
(فقط بعد از چک pid ست می‌شود)، VM زنده (خواندن بی‌ضرر داخل image). جالب
اینکه «تقاطع sys==M1» که طراحی کرده بودم عملاً باگ را تأیید می‌کرد — هر دو
برابر بودند چون VA سمبل پاس می‌شد!

پنجره‌ی نام 0x560..0x5D8 هم بررسی و **تبرئه** شد: با سه منبع مستقل
(خروجی WinDbg از کتاب Evading EDR: `+0x5a8 ImageFileName : [15]`، جدول
آفست‌های عمومی 19045) تأیید شد که ImageFileName در 19041–19045 واقعاً در
**0x5A8** است — همان چیزی که v23 فرض کرده بود. تنها باگ، deref بود.

## درایور v24 چیست؟

**v23 + زنجیره‌ی deref — به شکل تابع اشتراکی:**

```c
// pw::SysEprocessFromSymbol (ProcessWalk.h — درایور و هارنس یکی‌اند)
S1: kx::Resolve("PsInitialSystemProcess")          // داخل image، بودجه‌دار
S2: kx::Rd32(rva) + kx::Rd32(rva+4)                // خواندن گیت‌شده‌ی خانه → eproc
    → pw::WalkCore(eproc)                          // هدفِ deref‌شده خودش اعتبارسنجی می‌شود
```

خواندن خانه از همان مسیر گیت‌دارِ داخل-image همه‌ی خواندن‌های اکسپورت
می‌رود — **بدون ریشه‌ی اعتماد جدید** — و WalkCore خودش هدف را وارسی می‌کند
(کانونیکال + pid==4 + سازگاری LIST_ENTRY دوسویه + پنجره‌ی pool±4GB + بودجه‌ها).
ترس سریال جدید: `[PW] eproc=` بعد از `[PW] sys=` (ترس sys دست‌نخورده = همان
تقاطع M1).

## اسکریپت v32: انتظارات W1 اصلاح شد (مهم!)

اسکریپت v31 در مسیر موفقیت W1 انتظار **اشتباه** داشت: `entries[0].eproc == M1`
(همان تصورِ سمبلی که باعث باگ درایور شد!). v32 آن را به معنای درست v24
تغییر داد:

- `sysEntry@1032` = **EPROCESS با-deref-شده**: کانونیکال + **بیرون از**
  `[pe_base, pe_base+pe_size)` + `== entries[0].eproc` با pid 4
- تقاطع سمبل (sys==M1) روی **سریال [PW] sys=** خوانده می‌شود نه payload
- INFCNT با wSent=6 (وقتی W کامل سبز شود): **G+8+13+4+6 = 33**

## انتظار اجرای v32

- **M1..M4**: مثل v31 سبز (رگرسیون — فیکس اکسپورت دست‌نخورده)
- **W1**: `status=1` + `payload.status=0` + `eproc=0xFFFF8E...` (کانونیکال،
  **بیرون از image**) + `count` ۳۰..۶۴ + `entries[0]` = System (pid 4) روی
  خودِ eproc + نام‌ها در 0x5A8 با flags=1 (اولین نام = "System") + سریال
  `[PW] sys=` == مقدار M1 و `[PW] eproc=` == مقدار payload
- **W2**: تطبیق با Get-Process زنده (تلورانس ≤3)
- **W3**: pid خودِ PowerShell در لیست (یا NOTE اگر انتهای لیست ۶۴تایی است)
- **W4a/b**: `ErrInvalid(5)` تمیز
- **W5**: با pid واقعی هم Success
- **INFCNT**: **33** = G+8+13+4+6 (با wSent=6)
- حکم پایانی: `>>> F3 PROVEN: THE EPROCESS WALK - PROCESS DATA OUTSIDE THE IMAGE <<<`

## اگر W باز هم رد شد (نباید، ولی اگر شد)

payload.status دقیقاً می‌گوید کدام گِیت: `2` resolve/deref رد شد (نباید)،
`3` هدف غیرکانونیکال، `4` not-System (اگر دیدید یعنی deref هنوز نرسیده —
هش بات را ببینید)، `5` لیست شکسته، `6` پنجره‌ی pool±4GB (روی VM تازه‌بوت
نباید)، `7` بودجه. هر امتناعی تمیز است و VM زنده می‌ماند — طبق ۶۶/۶۶
هاست‌تست. مثل همیشه: خروجی .txt + serial-phase-d.log + عکس بفرستید.

بعد از سبز شدن F3: قدم بعدی **F4 (پایه PTE/جدول صفحه — اعتبارسنجی residency
واقعی برای VAهای دلخواه)** و بعد **Infinity.exe** (کلاینت user-mode روی
همین حمل‌ونقل ring) است.
